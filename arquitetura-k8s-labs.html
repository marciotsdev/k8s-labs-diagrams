Decisões de arquitetura

Storage compartilhadoimplementado

O workspace do Tekton (shared-data) precisa ser visível por Tasks em Pods diferentes — exige volume compartilhado entre nodes, não disco local. Escolha: VM dedicada (nfs-ganesha) rodando NFS-Ganesha, consumida via csi-driver-nfs, substituindo o local-path-provisioner padrão do k3s, que prendia cada PipelineRun ao node do primeiro pod. É essa troca que viabilizou o balanceamento real entre k8s-ci-w1 e k8s-ci-w2.

Custo aceito: VM única é um ponto único de falha. Plano de mitigação: substituir por Longhorn (storage distribuído, replicado entre os próprios nodes) — em estudo, ver sequência de evolução do ambiente.

Isolamento de performanceimplementado

Nem tudo que é escrito no workspace precisa atravessar Pods: o node_modules da Task test não é lido por nenhuma Task posterior (a Task build reinstala de dentro do Buildah). Isolado num emptyDir local em vez do NFS compartilhado.

Medido antes/depois: test caiu de ~15min para ~4min; sca, que chegava a travar com timeout lendo pela rede, caiu para menos de 1min.

gVisor seletivoimplementado

Isolamento extra de syscalls aplicado só nas Tasks test, sast e sca — não precisam de mount privilegiado. A Task build fica de fora por necessidade, não por escolha: Buildah exige SYS_ADMIN e mount privilegiado, incompatível com o kernel de espaço de usuário do runsc.

Patch de imagem (Copacetic / Chainguard)avaliado, descartado

Copacetic: baixo ganho real — o rebuild + apt upgrade que a Task build já faz cobre a mesma superfície que o Copacetic cobriria.

Chainguard/Wolfi: base zero-CVE, mas troca a libc pra musl — reabre risco de módulo nativo quebrar, e exigiria multi-stage build. Os dois avaliados em 21/11/2026, nenhum implementado.

IaC Scan — gap do Terraformparcial, em avaliação

Checkov cobre Kubernetes (90 checks) e Ansible (24 checks) do próprio repo, mas zero regras pro provider Proxmox (bpg/proxmox) — confirmado via checkov -l | grep -i proxmox, contra um catálogo de +7900 checks organizados por provedor de nuvem. Proxmox é provider de nicho, fora desse catálogo.

Em avaliação (22/11/2026): tfsec/trivy config como alternativa — mesmo risco de repetir o gap, já que a maioria das regras built-in também é por provedor de nuvem. Próximo passo: rodar e ver o que dispara de verdade.

kube-bench como CronJob, não Taskimplementado

Hardening (CIS Benchmark) não cabe no modelo Tekton Task: não existe "git push" que signifique "configuração do cluster mudou" — isso acontece via Terraform/Ansible apply, fora do fluxo de entrega. Implementado como CronJob, mesma família do Pruner, 1 por node (6 no total, 2 clusters).

Risco aceito: não existe perfil k3s-cis-* exato pra k3s v1.37.x — usado k3s-cis-1.24 (mapeado oficialmente até v1.32), aproximação consciente dado o caráter de estudo do ambiente.

Semaphore nunca se autogerencialimitação conhecida

O binário Go do Semaphore mata o próprio job em andamento ao receber SIGTERM quando o serviço reinicia. Por isso o playbook que instala/configura a própria VM do Semaphore só roda manualmente, via terminal — nunca através do próprio Semaphore.

Cilium substitui o Flannelimplementado 23/11

O Flannel embarcado do k3s (modo VXLAN, sem motor de política) aceitaria um NetworkPolicy sem erro, mas ele ficaria completamente inerte — falsa sensação de isolamento. Decisão: adiantar o Cilium no k8s-backstage (fora da ordem original do roadmap de evolução), já que o multi-tenancy por estágio exige rede real entre namespaces.

Gotcha real, não documentado com clareza: o k3s usa um diretório de config de CNI próprio (/var/lib/rancher/k3s/agent/etc/cni/net.d/), diferente do /etc/cni/net.d/ genérico que o Helm chart do Cilium escreve por padrão. O Cilium "funcionava" (pod Running, cilium status OK) mas o kubelet nunca via a config — corrigido com cni.confPath/cni.binPath explícitos no Helm.

Argo CD Image Updater — write-back via SSHimplementado 23/11

Estratégia digest, não semver: o Tekton sempre publica a mesma tag fixa (:latest), então só o conteúdo por trás dela muda. Write-back via Git (mantém a filosofia do projeto: Argo CD só compara Git vs. cluster, nunca aplica direto).

HTTP não foi opção: o método git:secret: do Image Updater v1.5 só reconhece https:// ou SSH — nunca http:// puro (confirmado lendo o código-fonte do provider), e o Forgejo deste lab não tem TLS. Solução: deploy key dedicada, só com escrita no gitops-manifests, via porta 2222.

Multi-tenancy por estágioimplementado 23/11

Tenant = estágio (dev/qa/stage/prod), não time/projeto — decisão explícita antes de implementar. Cada namespace: ResourceQuota (teto agregado, números escalonados 1→4 vCPU/GB), LimitRange (default + teto por container) e 4 NetworkPolicy (default-deny, same-namespace, dns-egress, ingress-from-traefik).

Validado com teste real, não só "objeto existe": dev → qa deu timeout silencioso (pacote derrubado); dev → dev deu "connection refused" (pacote chegou, só não tinha servidor ouvindo) — a diferença entre os dois comprova o isolamento de rede de verdade.

Emuladores de nuvem local (MiniStack / floci-az)pendente de integração

Base pro Crossplane validar infra de tamanhos diferentes por estágio sem custo real de cloud. AWS via MiniStack confirmado por pesquisa (provider-family-aws + provider-aws-s3/dynamodb, v2.10.0) — falta só confirmar suporte a endpoint customizado na prática.

Azure via floci-az tem um bloqueio real: os providers Azure oficiais da Crossplane (Upjet, embrulham o azurerm do Terraform) só falam com o Azure Resource Manager real + Azure AD, sem campo de endpoint customizável — e o floci-az não é um emulador de ARM. Caminho em avaliação: provider genérico provider-http chamando a API própria do floci-az diretamente, em vez de fingir que ele é Azure de verdade.

Wazuh — consolidação em vez de ferramenta por camadaimplementado 24/11

Avaliado como SIEM durante um exercício de cobertura de cyber security, com um critério explícito: priorizar o maior ganho de consolidação em vez de instalar mais uma solução isolada por camada. Resultado: Wazuh substitui duas peças já planejadas/em uso, não só soma uma terceira.

SCA substitui o Lynis (mesmo CIS Benchmark de SO, com compliance mapping nativo PCI-DSS/SOX/HIPAA que o Lynis nunca teve — fecha de quebra o gap que a ideia antiga "Ansible+Rundeck+OpenSCAP" tentava cobrir, hoje obsoleta). Wazuh Indexer (fork do OpenSearch) substitui o Loki/Fluent Bit planejado como log centralizado — trade-off aceito: bem mais pesado que o Loki (JVM, ~2-4GB só pro Indexer). Falco não é substituído — o módulo de container do Wazuh é raso (só eventos da API do Docker); quando implementado, vira log source consumido pelo Wazuh, não dashboard isolado. kube-bench continua intacto (audita Kubernetes, camada diferente do SCA).

VM 2031/.80 (8 vCPU/8GB/100GB, faixa 26-50 agentes — folga de propósito). 3 gotchas reais no caminho: (1) path do repo apt é 4.x fixo, não 4.14 versionado (403/AccessDenied do S3 com o path errado); (2) Manager+Indexer falharam no primeiro boot — o JVM do OpenSearch bateu no timeout de 3min do systemd competindo com o resto do boot da VM, corrigido reiniciando isolado (indexer antes do manager); (3) enrollment de agente falha silenciosamente se o Manager estiver fora do ar na instalação, mas o agente tem retry automático (~40-50s) e se autorregistra sozinho assim que o Manager volta — nenhum dos 10 agentes precisou de intervenção manual. 10/10 confirmados Active, SCA já rodando a política CIS Ubuntu 22.04.

qemu-guest-agent faltando em 4 VMs standalonecorrigido 24/11

Achado ao notar no Proxmox UI que floci-az e wazuh apareciam sem o guest agent. Investigação mostrou que era mais amplo: só o role k3s-cluster e o nfs-ganesha instalavam qemu-guest-agent — ministack, floci-az, semaphore e o novo wazuh-manager nunca tiveram esse passo, mesmo sendo um bug real já documentado (e corrigido) no nfs-ganesha em 2026-11-19 ("terraform apply" trava esperando o IP de volta sem o agente). Replicado o mesmo par de tasks nos 4 roles que faltavam.
